# Unified Service Scheduler Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Scheduler Service backend: a REST API that books a bay + qualified technician for the full service duration with zero double-booking, Redis slot holds, logical CQRS, a transactional outbox, and a one-command local Docker stack with logs in OpenSearch.

**Architecture:** One Spring Boot app split into command (writes → PostgreSQL primary) and query (reads → replica + Redis) packages. Correctness lives in a PostgreSQL `EXCLUDE` constraint on `resource_reservation`; Redis holds and the slot ledger only make conflicts fail fast. Every state change writes an outbox row in the same transaction; a relay publishes it through an `EventPublisher` port (logging adapter built).

**Tech Stack:** Java 21, Spring Boot 3.5.6 (web, jdbc, data-redis, validation, actuator), PostgreSQL 16, Redis 7, Flyway, springdoc-openapi 2.8.13, logstash-logback-encoder 8.1, uuid-creator 6.1.1 (UUIDv7), JUnit 5, AssertJ, Testcontainers 1.21.3, RestAssured, ArchUnit 1.4.1, Maven (wrapper 3.9.9), Spotless (google-java-format 1.28.0), Checkstyle 10.26.1, JaCoCo 0.8.13, OWASP Dependency-Check 12.1.3, Docker Compose.

**Spec:** `docs/system-design/02-detailed-design.md` (overview: `docs/system-design/01-high-level-design.md`) — section numbers below (§n) refer to it.

## Global Constraints

- API exactly as spec §14 (31 operations): conventions §14.1 (`/me` vs `/dealerships/{d}`, wrapped collections `{items, nextCursor}`, `ETag` on single appointments, `If-Match` required on PATCH/reschedule, optional on actions, `Idempotency-Replayed: true` on replays, merge-patch for PATCH, `Cache-Control` per §14.1, `X-Request-Id` echoed). Error `title`s and `detail` style per §14.6; `Retry-After` on 409 `REQUEST_IN_PROGRESS` (1 s) and 503 (`HOLDS_UNAVAILABLE` 30 s, `SERVICE_UNAVAILABLE` 5 s).
- Base package `com.keyloop.scheduler`; base path `/api/v1`; JSON only; errors are RFC 9457 `application/problem+json` with extra properties `code` and `traceId` (§14.6).
- Identity comes only from headers `X-User-Id` (UUID), `X-User-Roles` (`CUSTOMER`/`DISPATCHER`, comma-separated), `X-Dealership-Ids` (comma-separated UUIDs, staff only). Missing/malformed ⇒ `401 UNAUTHENTICATED`. No anonymous endpoints (§11).
- Customer resource owned by someone else ⇒ `404 NOT_FOUND`, never `403` (§11.3). Dispatcher path dealership not in `X-Dealership-Ids` ⇒ `403 FORBIDDEN`.
- All IDs generated by the app are UUIDv7.
- **UTC everywhere** (§7.3, §12.2): `timestamptz` columns `start_at`/`end_at` with a generated half-open `[start, end)` `tstzrange`; DB `timezone='UTC'`, JVM `-Duser.timezone=UTC`, Jackson writes `Instant`/`OffsetDateTime` as UTC `Z`. API accepts ISO-8601 with any offset and returns UTC `Z` plus the dealership's `timeZone`. Opening hours are the only local wall-clock data.
- Integrity enforced in SQL (§7.1): reservation has `service_bay_id` XOR `technician_id` (real FKs) with generated `resource_id`; composite FKs `(bay|technician, dealership_id)` and `(vehicle_id, customer_id)`; no `ON DELETE CASCADE`.
- Indexes exactly as §7.2 (GiST `reservation_dealership_window`, `reservation_by_appointment`, `text_pattern_ops` prefix indexes, covering `appointment_dealership_day`, `appointment_customer_timeline`).
- Business "now" = PostgreSQL `now()` (§12.3); hold expiry = Redis `TIME`.
- Customer policy: start ≥ now + 2h, ≤ now + 60 days, whole job inside one day's opening hours, change/cancel only `BOOKED` and ≥ 24h before start. Dispatcher policy: start ≥ now − 15 min, ≤ now + 60 days, start inside opening hours, end may pass closing, no cutoff; `IN_PROGRESS`/`ON_HOLD` start is fixed (§6.4).
- 1–5 distinct service types per booking; duration = sum; bay period = period + `bay_buffer_minutes` (0–60).
- Availability: 15-minute candidate starts, range `from..to` max 14 days; alternatives = nearest 5 starts after the requested one.
- Allocation: max 3 attempts; reservations inserted/updated ordered by `resource_id`; one `40P01` retry.
- Holds: TTL 10 min; one active hold per user per dealership-day; ledger marker TTL 10 min; catalog cache TTL 10 min; Redis command timeout 100 ms.
- `Idempotency-Key` required on `POST …/appointments` (else `428`); `If-Match` required on `PATCH` (else `428`); version mismatch ⇒ `412 VERSION_CONFLICT`.
- No-show allowed only after start + 30 min. Archival deletes reservations ended > 30 days; idempotency keys expire after 24h.
- **Two test suites, both mandatory:** unit tests `*Test` (Surefire, plain JUnit + Mockito, no Spring context, no Docker, < 1 s each) and integration tests `*IT` (Failsafe, `IntegrationTest` base, real PostgreSQL + Redis via Testcontainers). Every task ships **both**: unit tests for its logic, integration tests for its SQL/Redis/HTTP behaviour.
- **Coverage gates (JaCoCo, fail the build):**
  - **Unit gate — unit tests alone: ≥ 90 % LINE and ≥ 80 % BRANCH** over all classes except those that only make sense against real infrastructure: `*Controller`, `*Repository`, `IdempotencyStore`, `SlotLedger`, `LedgerOccupancySource`, `*Config`, `SchedulerApplication`. Those are covered by the integration gate.
  - **Overall gate — unit + integration merged: ≥ 90 % LINE** over every class except `SchedulerApplication`.
- Other build gates in `./mvnw verify`: Spotless check, Checkstyle (Google checks, fail on violation), ArchUnit.
- **Concurrency suite (double-booking proof):** every concurrency IT fires requests from a `CountDownLatch` start gate on ≥ 2 threads per contended resource, and **ends with `NoDoubleBookingAssert.verify(jdbc)`** (no overlapping active reservations per resource; every active appointment has exactly one active bay and one active technician reservation matching its times). Contention tests run as `@RepeatedTest(5)`. All concurrency ITs are tagged `@Tag("concurrency")` and runnable alone with `./scripts/it.sh '*Concurrency*IT'`.
- Every task's final step before commit runs `./mvnw verify` (both suites + both gates) — a task is not done if coverage drops below the gates.
- Running one suite while developing: unit `./mvnw -q test -Dtest='<pattern>'`; integration `./scripts/it.sh '<pattern>'` (Task 1).
- Docker images pinned: `postgres:16.4-alpine` (tests), `bitnami/postgresql:16.4.0` (compose primary/replica), `redis:7.4.1-alpine`, `opensearchproject/opensearch:2.17.1`, `opensearchproject/opensearch-dashboards:2.17.1`, `fluent/fluent-bit:3.1.9`, `eclipse-temurin:21.0.5_11-jre-alpine`.
- Logs never contain email, phone, name or VIN — only IDs.

## Review Focus

1. A start sent with a non-dealership offset (`2026-11-02T16:00:00+07:00` for a `Europe/London` dealer) must be accepted as the same instant and echoed back as `2026-11-02T09:00:00Z` — test in Task 7.
2. A date when the dealership is closed (no `opening_hours` row) must give `422 OUTSIDE_OPENING_HOURS` on booking and an empty `starts` list (not an error) in availability — tests in Tasks 7 and 8.
3. Availability with `from > to`, a range over 14 days, or unparseable `serviceTypeIds` must be `400 VALIDATION_ERROR` — test in Task 8.
4. Duplicate service IDs, more than 5, or a service the dealership doesn't offer must be `400`/`422` before any allocation — test in Task 7.
5. DST spring-forward day (`Europe/London`, 2027-03-28, opening 00:30–03:30 in a fixture) must never offer `01:00`–`01:45` local — test in Task 8.
