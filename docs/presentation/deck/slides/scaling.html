SCALING AND REPLICATION

Reads and writes take different paths

Reads · ~10k/s (CQRS)

  • Free times ⇒ Redis slot ledger, no DB
  • Gantt board ⇒ read replicas, lag < 1 s; stale edits get 412
  • My appointments ⇒ primary, so you see what you just booked

Writes · ~1k/s

  • One primary per region: ~330 writes/s, far below its limit
  • Conflicts stay inside one dealership
  • If a region outgrows it: shard by dealership_id

Pods

stateless, HPA on CPU + RPS, min 3

PgBouncer

more pods, same DB connections

Replicas

2 ⇒ 6 on CPU or lag

Redis

cluster, 3 shards; if down, read the DB

Built: primary / replica routing, Redis ledger + cache · Designed only: HPA, PgBouncer, sharding · 5

(~25s) How it scales. Reads and writes go different ways. Free times come from Redis, so they don't touch the database. The dispatcher board reads from replicas; they can be a second behind, and that's fine, because an old version can't overwrite a newer one. Your own bookings always read from the primary, so you see them right away. Writes are small: about three hundred per second per region, easy for one database. If a region ever grows too big, we split by dealership. Pods, replicas and Redis all scale out on their own.
