THE ROLE OF REDIS

Redis makes it fast; the database decides

1 · Slot ledger

Each bay's and technician's day in memory. Free times need no DB query.

2 · 10-minute holds

One Lua script takes a bay + technician. Taken ⇒ 409 in ~1 ms, never reaches PostgreSQL.

3 · Read cache

Services, bays, technicians, opening hours. 10-minute TTL.

If Redis is wrong or down……what happens
Loses holds after a failoverEXCLUDE rejects at confirm ⇒ 409; ledger rebuilt from the primary
Misses an update after a crashThe next DB conflict marks the ledger stale; it heals itself
Is completely downBooking and free times go to the DB: slower, still correct

Built and tested · one dealership-day per hash tag, so the Lua script stays atomic in a cluster · 10

(~25s) Redis has three jobs, all about speed. First, it keeps each dealership's day in memory, so showing free times needs no database query. Second, it holds a slot for ten minutes. If the slot is already taken, the customer gets an answer in about a millisecond, and the database never sees that request. Third, it caches things that rarely change, like services and opening hours. But Redis never decides. If it loses data, the database still blocks the overlap. If it goes down, everything still works, just slower.
